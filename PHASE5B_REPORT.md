# Phase 5B Report — Checkout, transactional order creation and success scene

Spec: §4.2–§4.11, §6.7, §8, §11.8 (M60–M63). Highest-risk phase: correctness first.

## What was built
- **`OrderService::create()`** (the transactional core): one DB transaction with the deterministic lock order from §4.3 — stock rows (products, then variants) locked by ascending id first, then the coupon row `lockForUpdate`. Inside the transaction it revalidates every line against the locked rows (active product/variant, quantity min/step/max, stock), recomputes pricing (sale + quantity tier) via `PricingService`, revalidates the coupon and shipping (free-shipping rule §4.4, governorate must be active), and only then creates the order: order number assigned by the existing model hook in the same transaction, immutable order-item snapshots (name, variant, SKU, `unit_code` + Arabic label, unit price, **cost price**, decimal quantity, line total), decimal stock deduction with `stock_movements`, coupon `used_count` incremented exactly once, and the first `order_status_histories` row. `sales_count` is **not** touched here — it moves only on delivery (§4.7). Any failure throws `App\Exceptions\OrderException` (Arabic key + offending product name) and the transaction rolls back with nothing saved.
- **`/checkout` (`CheckoutPage` Livewire, one page)**: guest checkout, account never required. Required name, Egyptian mobile (validated with `Phone::isValidMobile` after Arabic-digit normalization), governorate select from active `shipping_rates` (live fee + estimated delivery days update), city, detailed address; optional email, second phone, notes. Logged-in users are prefilled from their profile / default address (guarded by `Schema::hasTable('addresses')` since account pages arrive in Phase 7). Payment radios come from settings (COD default, bank transfer shows `bank_transfer_details`, card hidden while `payment_card_enabled` is false). CSRF, honeypot (pretend-success, creates nothing), throttle (10/min/IP) and an idempotency token per checkout session: a duplicate submit with the same token replays to the first order's success page instead of creating a second order. The cart is cleared and the success-session flag set **only after** the transaction commits. Non-purchasable cart lines block submission with a clear Arabic error before the transaction starts.
- **`/order/success/{order_number}`** (`OrderSuccessController`): visible only to the session that created the order (`order.success.{number}` flag) or the owning user — anything else gets 403. M63: the `success` E16 scene (plug slides in, spark, bulb flickers and lights) renders only here, after the order is committed, with the order number + copy button ("تم النسخ" feedback), totals from the immutable snapshots, item lines with units, and a prefilled WhatsApp follow-up link.
- M60: the confirm button shows the bolt-loader + "جاري تأكيد الطلب…" while submitting. M61: the form shakes (transform-only, finite) when server errors come back. M62: totals cross-fade via the existing opacity-only totals flash when the governorate changes.
- New Arabic strings in `lang/ar/store.php` for all checkout/success/error copy.

## NOT RUN / notes
- **True MySQL concurrency** (two simultaneous transactions racing stock / a `usage_limit=1` coupon): NOT RUN — the test database here is SQLite, which cannot reproduce InnoDB row-lock contention. The sequential equivalent is covered (usage_limit=1 test, in-transaction rollback test); the lock order and `lockForUpdate` calls are in place for MySQL.
- Real-browser checkout / success-scene animation: NOT RUN (no browser in this environment). No animation delays or alters any money/stock/order step — the M63 scene renders only on the post-commit success page.
- Card payment flow (Paymob) is Phase 10; in 5B the card method is only created as a pending order if the owner enables it, with no gateway call.
